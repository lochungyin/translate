# 快捷翻译浮窗修复与验证

日期：2026-10-14（Asia/Shanghai），macOS aarch64。

最新结论：修复应用包签名、重新绑定辅助功能授权并重启后，进程检测为受信任。用户随后用实体键盘确认：在其他应用选中文字并按 Command + 反引号，翻译浮窗出现并显示译文。当前 macOS 包的划词快捷键已完成人工验收。

## 原因与修复

- 划词进程未被 macOS 视为受信任的辅助功能客户端，或选区为空时，原生后端主动调用 `config_window()`，误开工作台。现在只打开翻译浮窗，保留可输入区域并显示明确原因。
- 原有错误事件会早于首次创建窗口的监听器。现在原生保存带序号的完整翻译请求和错误；浮窗先订阅再读取快照，忽略重复或过期请求。`get_text` 继续兼容既有调用。
- 输入翻译、普通文字翻译及图片翻译共用浮窗请求路径；原生负责显示和聚焦，仍遵守普通翻译的隐藏窗口偏好，输入和错误提示始终可见。
- 浮窗的失焦、聚焦、移动及缩放监听改为当前窗口范围。
- 热键设置明确显示停用状态并提供“恢复默认”。本机输入翻译快捷键原来保存为空，已通过原生设置界面恢复为 `Alt+A`；划词保留 Command + 反引号。

## 已验证

- `pnpm test`：12 项通过；`pnpm build`、`cargo check --locked`、Rust 格式检查通过。
- `pnpm tauri build --debug --bundles app` 成功，并退出旧进程、重新启动输出的 `src-tauri/target/debug/bundle/macos/SuiTranslate.app`。重启前用户确认有道设置已保存。
- 原生热键页面真实显示输入翻译停用；点击“恢复默认”后显示 `Alt+A` 和“快捷键注册成功”，配置已落盘。
- 通过本机 HTTP `/selection_translate` 进入真实划词处理函数。系统 API 返回当前进程未受信任，浮窗显示权限原因；工作台完全关闭后重复调用，也只创建 `translate` 窗口，没有重新创建工作台。后续检查确认系统设置开关实际已开启，不能把 API 返回 false 直接解释为用户没有开启权限。
- 同一浮窗调用 `/input_translate` 后旧错误消失，输入框为空并获得焦点。
- 在原生浮窗输入 `Good morning.` 并按 Enter，Google 与用户已配置的有道均显示真实译文 `早上好。`；相同文本再次提交仍获得译文。
- 自动化检查期间临时关闭了“失去焦点时关闭窗口”，因为检查工具切换焦点会关闭浮窗；检查结束后已通过原生设置界面恢复开启。该设置关闭时的验证不能证明实体键盘触发或失焦自动关闭行为已验收。

## 首次检查时待验证（后续结果见下文）

- 自动化按键 `Alt+A` 未触发 macOS 全局快捷键，不能以注册成功或 HTTP 调用证明实体键盘触发成功；需要用户实际按键确认。
- 应用启动日志及原生错误界面仅确认当前进程未受信任。系统设置中的 SuiTranslate 开关实际已开启，后续诊断与签名修复见下文；真实取词仍待授权重新绑定后验证。
- 选区为空分支已修复，但当前无辅助功能权限，实际调用先进入权限错误分支，未单独实测空选区。
- Windows/WPS、Linux 尚未在本次修复中实测或重新打包。

## 已允许仍检测失败：签名诊断与修复

用户指出已允许辅助功能后，实查系统设置确认 SuiTranslate 开关为 on。通过该授权条目的“在访达中显示”和文件简介核对，路径就是当前运行的 `src-tauri/target/debug/bundle/macos/SuiTranslate.app`，不是另一份应用副本。

原包存在明确的签名缺陷：

- `codesign --verify --deep --strict` 失败，原因是 `code has no resources but signature indicates they must be present`。
- 主程序只有 `adhoc,linker-signed` 签名，标识为 `sui_translate-d9b9ccd16f184e07`，与 Info.plist 中的 `com.lochungyin.sui.translate` 不一致；Info.plist 未绑定，资源未封印。
- 指定要求只有代码哈希。当前机器没有可用的开发者签名证书，重新编译会改变这类签名的哈希；已有开关不能证明当前编译产物满足授权中记录的代码要求。

macOS 平台配置现增加 `signingIdentity: "-"`，让 Tauri 在打包完成后签署主程序和整个应用包。重新构建后，完整性校验通过，签名标识为 `com.lochungyin.sui.translate`，Info.plist 已绑定、资源已封印，并已启动此修复包。划词入口增加实时信任检查日志，提示区分“当前进程未受信任”和“用户没有开启开关”。

修复包首次启动仍报告 `MacOS Accessibility Trusted: false`。受系统保护的 TCC 数据库无法读取，未直接比对旧授权的代码要求。当前仍为本地 ad-hoc 签名，不能承诺未来重新编译后自动继承授权；跨版本稳定身份需要固定的有效签名证书。

### 授权重新绑定结果

用户明确允许重新绑定后，移除旧 SuiTranslate 条目；macOS 要求触控 ID／登录密码验证，用户完成系统验证并确认继续。随后通过系统文件选择器添加完整路径的当前修复包，界面显示 SuiTranslate 开关为 on。

退出并重新启动同一应用后，2026-10-14 14:45:22（Asia/Shanghai）的启动日志明确为 `MacOS Accessibility Trusted: true`，后续划词请求的实时日志也为 true。签名修复及授权重新绑定已恢复当前进程的辅助功能信任。

跨应用自动化测试创建了 TextEdit 的独立未保存测试文档“未命名2”，内容为 `Good morning.`。测试工具的无障碍树显示文字被选中，但通过本机 HTTP `/selection_translate` 进入实际取词函数后，选区仍为空，`selection` 库记录 `No selected text`。自动化组合键也未触发原生全局快捷键；测试工具的坐标输入报 `noWindowsAvailable`，无法可靠确认实际前台焦点。此结果不能证明实体键盘取词成功，也不足以证明用户实际取词仍然失败；需用户实体按键结果继续定位。

本次检查临时关闭的“失去焦点时关闭窗口”已通过原生设置界面恢复开启。签名通过校验且已授权的应用没有再次重新编译。

### 实体按键人工验收

用户收到“在其他应用中实际选中文字，再按 Command + 反引号”的验证请求后，明确确认“浮窗出现并显示译文”。这完成了当前包的跨应用划词快捷键人工验收；前述自动化空选区及无法模拟全局按键的结果仍保留为测试工具限制，没有用自动化结果代替用户实测。未采集用户实际选区内容。
